# Immutable Audit Trail Plan

## Current State (Phase 9E)

The current Clinic CRM audit system is **localStorage-based and mutable**:
- Audit logs stored in `clinic_crm_audit` localStorage key
- Security events stored in `clinic_crm_security_events` localStorage key
- Admin operations stored in `admin_audit` localStorage key
- All logs can be modified or deleted by admins
- No cryptographic integrity verification
- No append-only guarantees
- No server-side timestamps or signatures

## Limitations

1. **Mutable Storage**: localStorage can be modified by client-side JavaScript
2. **No Integrity**: No hash chaining or tamper detection
3. **No Server Authority**: All timestamps are client-generated
4. **No Append-Only**: Logs can be deleted or modified
5. **No Cryptographic Proofs**: No digital signatures or hash chains

## Future Backend Requirements

### 1. Append-Only Audit Log Storage

**Design:**
- Audit logs stored in append-only database tables
- Once written, entries cannot be modified or deleted
- Soft delete only (mark as deleted, preserve original)
- Immutable record of all system operations

**Implementation:**
```sql
CREATE TABLE audit_logs (
  id BIGSERIAL PRIMARY KEY,
  sequence_number BIGINT NOT NULL UNIQUE,
  timestamp TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  actor_id VARCHAR(255) NOT NULL,
  actor_role VARCHAR(50) NOT NULL,
  action VARCHAR(100) NOT NULL,
  module VARCHAR(50) NOT NULL,
  resource_type VARCHAR(100),
  resource_id VARCHAR(255),
  status VARCHAR(20) NOT NULL,
  metadata JSONB,
  hash VARCHAR(64) NOT NULL, -- SHA-256 of entry content
  previous_hash VARCHAR(64), -- Chain to previous entry
  signature TEXT, -- Optional: cryptographic signature
  server_id VARCHAR(100) NOT NULL, -- Server instance identifier
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_audit_logs_sequence ON audit_logs(sequence_number);
CREATE INDEX idx_audit_logs_timestamp ON audit_logs(timestamp);
CREATE INDEX idx_audit_logs_actor ON audit_logs(actor_id);
```

### 2. Hash Chaining for Integrity

**Design:**
- Each log entry includes SHA-256 hash of its content
- Each entry includes hash of previous entry (chain)
- Tampering breaks the chain and can be detected
- Periodic integrity verification

**Algorithm:**
```
entry.hash = SHA256(
  entry.sequence_number +
  entry.timestamp +
  entry.actor_id +
  entry.action +
  entry.module +
  entry.resource_type +
  entry.resource_id +
  JSON.stringify(entry.metadata)
)

entry.previous_hash = previous_entry.hash
```

**Verification:**
```
function verifyChain(entries) {
  for (let i = 1; i < entries.length; i++) {
    if (entries[i].previous_hash !== entries[i-1].hash) {
      return false; // Chain broken
    }
    const computedHash = computeHash(entries[i]);
    if (computedHash !== entries[i].hash) {
      return false; // Entry tampered
    }
  }
  return true;
}
```

### 3. Server-Side Timestamps

**Design:**
- All timestamps generated by server (not client)
- Use database `NOW()` or application server time
- Include server ID for distributed systems
- Clock synchronization via NTP

**Benefits:**
- Prevents timestamp manipulation
- Provides authoritative time source
- Enables temporal ordering across servers

### 4. Cryptographic Signatures (Optional)

**Design:**
- Each log entry signed with server private key
- Public key verification for authenticity
- Key rotation support
- HSM integration for key protection

**Implementation:**
```typescript
interface SignedAuditEntry extends AuditEntry {
  signature: string; // RSA/ECDSA signature
  key_id: string; // Key version identifier
  algorithm: string; // e.g., "ES256"
}
```

### 5. Immutable Security Events

**Design:**
- Security events stored in separate append-only table
- Higher integrity requirements
- Immediate write to persistent storage
- Replication to backup systems

**Schema:**
```sql
CREATE TABLE security_events (
  id BIGSERIAL PRIMARY KEY,
  sequence_number BIGINT NOT NULL UNIQUE,
  timestamp TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  event_type VARCHAR(100) NOT NULL,
  severity VARCHAR(20) NOT NULL,
  source_ip VARCHAR(45),
  user_agent TEXT,
  actor_id VARCHAR(255),
  metadata JSONB,
  hash VARCHAR(64) NOT NULL,
  previous_hash VARCHAR(64),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### 6. Retention and Archival

**Design:**
- Configurable retention policies per log type
- Automatic archival to cold storage after retention period
- Immutable archive storage (WORM - Write Once Read Many)
- Compression for long-term storage

**Implementation:**
- Hot storage: Recent logs (e.g., 90 days) - fast access
- Warm storage: Medium-term logs (e.g., 1 year) - compressed
- Cold storage: Long-term logs (e.g., 7 years) - immutable archive

### 7. Audit Log Export with Integrity

**Design:**
- Export includes hash chain verification data
- Export includes server signatures
- Export format includes integrity metadata
- Recipients can verify export authenticity

## Migration Path

### Phase 1: Dual-Write (Frontend + Backend)
- Frontend continues writing to localStorage
- Backend API receives audit events
- Backend writes to append-only database
- Reconciliation process to sync historical data

### Phase 2: Backend Authority
- Frontend sends audit events to backend API
- Backend generates authoritative timestamps
- Backend returns sequence numbers
- Frontend stores reference in localStorage (read-only)

### Phase 3: Immutable Storage
- Migrate to append-only database schema
- Implement hash chaining
- Implement integrity verification
- Enable cryptographic signatures

### Phase 4: Frontend Read-Only
- Frontend reads from backend API only
- localStorage becomes cache only
- No direct write access to audit storage
- All writes go through backend API

## Current Demo-Level Readiness

The current frontend implementation provides:
- ✅ PHI/PII-safe logging (no sensitive data in logs)
- ✅ Admin operation audit trail
- ✅ Archive-before-clear behavior
- ✅ Retention policy support
- ✅ Typed confirmation for destructive actions
- ❌ No cryptographic integrity
- ❌ No append-only guarantees
- ❌ No server authority
- ❌ No hash chaining

**Status:** Demo-level audit readiness, suitable for local development and demonstration. Production deployment requires backend implementation with immutable audit trail.

## Recommendations

1. **Immediate (Phase 10):** Continue frontend hardening, ensure all logs are PHI-safe
2. **Short-term:** Design backend audit schema and API
3. **Medium-term:** Implement backend append-only audit storage
4. **Long-term:** Implement hash chaining and cryptographic signatures
5. **Ongoing:** Regular integrity verification and audit trail testing
